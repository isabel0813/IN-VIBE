# 뭐보뇽 · Frontend

React + Vite + TypeScript 웹앱과 Tauri 2 Windows 앱입니다. 기존 FastAPI를 사용하며 별도 프론트엔드 서버 저장소나 로그인은 없습니다. 데스크톱 실행·위젯 구조는 [데스크톱 안내](docs/desktop.md), 활동 감지·복구와 최신 검증 범위는 [Windows MVP 안내](docs/windows-mvp.md)를 참고하세요.

## 실행

Node.js 24 LTS 환경에서 검증했습니다.

```powershell
cd frontend
npm.cmd ci
npm.cmd run dev
```

브라우저에서 터미널에 표시된 주소(기본 `http://127.0.0.1:5173`)를 엽니다. macOS/Linux에서는 `npm.cmd` 대신 `npm`을 사용합니다. Windows에서 PowerShell 실행 정책으로 `npm.ps1`이 차단될 때도 `npm.cmd`로 실행할 수 있습니다.

백엔드는 별도 터미널에서 **8010 포트**로 실행합니다. 개발 기본 API 주소도 `http://127.0.0.1:8010`입니다. 백엔드 README의 기본 8000 포트로 실행하면 이 프론트엔드와 연결되지 않습니다. 이미 8010에서 정상 실행 중이면 중복 실행하거나 프로세스를 종료하지 마세요.

저장소 루트에서 Windows PowerShell로 실행합니다. 기존 `.venv`가 있으면 생성·설치 단계는 생략할 수 있습니다.

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8010
```

실행 파일이 `python` 대신 `py`로 설치된 PC는 가상환경 생성에 `py -m venv .venv`를 사용합니다. Windows의 `Asia/Seoul` 시간대에 필요한 `tzdata`는 현재 `backend/requirements.txt`에 포함되어 있습니다. API 키 없이도 직접 입력·저장·계획·완료·세션 생성/종료는 사용 가능합니다.

다른 터미널에서 `frontend`로 이동한 뒤 `npm.cmd run dev`(웹) 또는 `npm.cmd run desktop:dev`(Tauri)를 실행합니다. Tauri는 Vite도 시작하므로 두 명령을 동시에 실행하지 마세요. 이미 이 프로젝트의 Vite가 5173을 사용 중이면 해당 터미널의 서버만 먼저 종료하거나 기존 개발 앱을 사용합니다.

백엔드 주소를 바꾸려면 `.env.local`의 아래 값을 수정한 뒤 Vite를 재시작합니다. `.env.local`이 없다면 `.env.example`을 복사하되, 기존 파일을 덮어쓰지 마세요. `.env.local`은 Git에서 제외됩니다.

```dotenv
VITE_API_BASE_URL=http://127.0.0.1:8010
```

`VITE_` 환경변수는 클라이언트 번들에 포함됩니다. 비밀 키를 넣지 마세요. 다른 기기에서 접속할 때에는 해당 기기에서 접근 가능한 백엔드 주소와 백엔드 `CORS_ORIGINS` 설정이 필요합니다. 빌드 후에는 환경변수 변경 시 다시 빌드해야 합니다.

명시적 설정이 없을 때 개발 모드는 8010, production 빌드는 `https://api.mobonyong.com`을 사용합니다. **`.env.local`은 production 빌드에도 적용**되므로 로컬 검증용 빌드를 운영 배포로 혼동하지 마세요. 배포 환경에서는 `VITE_API_BASE_URL=https://api.mobonyong.com`을 명시해야 합니다. 현재 Tauri CSP는 운영 API와 로컬 8010을 모두 허용합니다.

### 연결 오류와 AI 설정 오류 구분

- `서버에 연결할 수 없어요`: HTTP 응답을 받지 못한 상태입니다. 8010 실행 여부, 실제 Vite의 API 주소, CORS를 확인하세요. 입력은 보존되며 자동으로 세션 생성을 재시도하지 않습니다. 전송 후 응답만 끊겼다면 서버 처리 여부는 알 수 없습니다.
- `서버에는 연결됐지만 AI API 키가 설정되지 않았어요`: `/tasks/parse` 또는 `/judge`에서 키 미설정 503을 받았습니다. AI 키는 **백엔드 프로세스의 `ANTHROPIC_API_KEY` 환경변수에만** 설정하고 백엔드를 재시작해야 합니다. 프론트엔드 `.env.local`이나 `VITE_` 변수에 넣지 마세요. 기존 [백엔드 AI 설정 안내](../backend/README.md)를 참고하세요.
- 기타 AI 503은 제공자 설정/사용 불가로 표시하며 키 미설정으로 단정하지 않습니다. 파싱 실패 시 원문을 유지한 직접 입력 화면으로 이동합니다. AI 실패는 저장·계획 API 실패와 별개입니다.

읽기 전용 연결 검사(임의의 새 사용자 ID 사용):

```powershell
$headers = @{ 'X-User-Id' = [guid]::NewGuid().ToString() }
foreach ($route in '/health', '/tasks', '/plan', '/settings') {
  Invoke-RestMethod -Uri "http://127.0.0.1:8010$route" -Headers $headers
}
```

`/health`만 성공해도 전체 기능이 정상인 것은 아닙니다. 나머지 3개 응답도 확인하세요. 사용자 헤더가 없으면 일부 API는 422를 반환합니다. 프론트엔드는 최초 UUID를 저장하고 자동으로 전달합니다.

## 기본 사용 흐름 (2026-11-12 뭐보뇽 기획)

1. C안 시작 화면에서 **지금 공부할 일 한 줄**(1~100자)을 입력합니다.
2. **집중 시작**으로 `POST /sessions`를 호출합니다. AI 파싱과 키가 필요하지 않습니다.
3. 서버 세션 ID와 작업명을 기존 집중 스토어에 연결하고, Windows에서는 메인 창을 숨긴 뒤 독립 안뇽이 위젯으로 이어집니다. 웹에서는 OS 창 제어 없는 위젯 미리보기입니다.
4. 위젯의 **집중 화면 보기**로 돌아오며 메인/위젯은 같은 작업과 일시정지 상태를 사용합니다.
5. 메인 또는 위젯에서 세션을 종료하면 로컬 집중 상태와 서버 세션을 종료합니다. 서버 종료에 실패해도 로컬 관측은 중지하고 오류를 안내합니다.

기본 화면과 설정, 위젯에서 복귀하는 흐름은 `/tasks`, `/tasks/parse`, `/plan`, `/settings`, `/plan/wasted`를 호출하지 않습니다. 기존 API는 삭제하지 않았습니다.

**설정 → AI 판단에 동의**와 **Windows 활동 감지/YouTube 연결 동의**는 각각 별개입니다. 어떤 동의도 세션 시작으로 자동 활성화하지 않습니다. AI 동의는 메인 컨트롤러가 실행 중일 때만 유지하며 앱 재시작 시 꺼집니다. 설정 화면 왕복으로 컨트롤러를 재생성하거나 세션을 새로 만들지 않습니다.

`CloudSession.tsx`의 `useCloudController`가 시작·종료·AI 판단을 담당하고, `App.tsx`는 C안 UI로 이를 사용합니다. 프로덕션 메인 창에는 컨트롤러를 하나만 둡니다. 위젯은 기존 스토어와 클라우드 상태를 구독하며 서버 세션을 생성하지 않습니다. 위젯 표시 실패 시 기존 세션을 유지하고 **위젯으로 돌아가기**로 표시만 재시도합니다.

## 기존 작업 데이터 확인 (기본 MVP 흐름 외)

기존 데이터는 삭제·이관하지 않았습니다. 세션 종료 후 **설정 → 기존 작업 데이터 → 기존 작업 보기**를 선택할 때만 `LegacyPlanner.tsx`와 관련 API를 불러옵니다. 새 기본 흐름에는 투두·마감·여유 시간·계획 복구 기능을 추가하지 않았습니다. 이전 화면의 동작은 다음과 같습니다.

1. 여러 할 일을 자연어로 적고 **AI로 할 일 정리**를 누릅니다.
2. AI의 추정 내용을 읽고 이름, 마감, 예상 시간, 중요도를 수정합니다. 초안은 확인 후 저장됩니다.
3. **저장하고 계획 보기**를 누르면 백엔드가 계산한 작업 순서, 지금 할 일, 여유 시간, 부족 시간을 표시합니다.
4. **작업 시작**으로 집중 상태를 표시하고, 완료 버튼이나 체크박스로 작업을 완료합니다. 완료 체크를 해제하면 계획에 다시 포함됩니다.

AI 오류(422/503), Ollama 미실행, 네트워크 오류 시 직접 입력 폼으로 전환됩니다. AI 응답 대기 중에도 직접 입력을 선택할 수 있습니다. 원문은 확인 화면에서 펼쳐 볼 수 있습니다. 직접 입력에는 AI가 필요 없지만, **저장과 계획 계산에는 FastAPI 연결이 필요합니다**. 실패한 저장은 초안을 유지하며, 성공한 저장 이후 조회만 실패한 경우에는 다시 연결할 때 중복 저장하지 않습니다.

## API 계약

기본 흐름: `POST /sessions`, `POST /sessions/{id}/end`, 별도 동의 후 `POST /judge`, 오탐 정정 시 `POST /judge/feedback`를 그대로 사용합니다. 아래는 이전 작업 화면에 보존된 계약입니다.

| API                 | 용도                                             |
| ------------------- | ------------------------------------------------ |
| `POST /tasks/parse` | `{ text }` → `{ drafts, assumptions }`           |
| `POST /tasks/batch` | `{ tasks: TaskDraft[] }` → 생성된 작업 배열      |
| `GET /tasks`        | 완료한 작업을 포함한 목록                        |
| `PATCH /tasks/{id}` | 작업 정보 수정 또는 `{ done: boolean }`          |
| `GET /plan`         | 작업 순서, 지금 할 일, 여유·부족 시간, 지난 마감 |
| `GET /settings`     | 내일 이후 계산에 쓰는 `daily_minutes` 읽기       |
| `POST /plan/wasted` | 사용자가 확인한 `{ wasted_minutes }` → 변화와 현재 계획 |

- 첫 요청에서 UUID를 생성하고 `localStorage`의 `in-vibe.user-id`에 저장합니다. 모든 요청에 동일한 `X-User-Id`를 보냅니다. 저장소를 지우거나 브라우저/접속 origin을 바꾸면 별도 사용자로 처리됩니다.
- 날짜 입력과 표시는 한국 시간(Asia/Seoul)입니다. 저장할 때 ISO 8601의 `+09:00`을 명시합니다.
- 서버 제약과 동일하게 작업 이름 1~100자, 예상 시간 5~6000분(정수), 일괄 등록 1~30개, 자연어 입력 2000자를 적용합니다.
- 계획 계산은 서버가 담당합니다. `free_minutes: null`, `now_task: null`, 지난 마감, 시간 부족, 빈 목록을 구분합니다. 지난 마감은 부족 시간 합산에 넣지 않습니다.
- 계획 화면은 1분마다, 창에 다시 포커스가 올 때, 저장·완료 변경 후 갱신합니다. 조회 실패 시 오래된 계획 대신 연결 안내를 표시합니다.
- 일반 요청은 15초, AI 파싱은 기본 Ollama 준비 시간을 고려해 130초까지 기다립니다. 백엔드 작업이 이미 처리된 후 응답만 끊긴 경우에는 자동 재전송하지 않습니다. 저장 응답이 시간 초과되었다면 재저장 전 나의 계획에서 저장 여부를 확인하세요.

## 코드 구조

```text
src/
  api/          # HTTP, 사용자 UUID, FastAPI 요청·응답 타입
  components/   # 초안 편집기, 계획 화면, 아이콘
  lib/          # 한국 시간 변환, 초안 검증·직렬화
  test/         # 테스트 공통 설정
  App.tsx       # C안 한 줄 집중 시작/종료와 설정
  LegacyPlanner.tsx # 명시적으로 선택한 기존 작업 화면
  styles.css    # 노트북 우선 다크 테마와 작은 화면 대응
```

UI와 HTTP 코드를 분리했습니다. 데스크톱에서는 `작업 시작` 시 독립 안뇽이 위젯을 표시하고 메인 창을 숨깁니다. Rust 메모리에서 세션을 공유하며 앱 재시작 후에는 자동 재개하지 않습니다. 웹에서는 OS 창 제어 없는 미리보기를 제공합니다. Windows에서는 명시적 동의 후 활성 창을 로컬 분류하고, 사용자가 확인한 이탈 시간만 계획 복구 API로 전달합니다.

## 검증

한 줄 집중 흐름 통합의 최신 검증은 [사용자 흐름 통합 기록](docs/unified-focus-flow.md)을 참고하세요.

C안 연결 점검의 실제 API/Windows 확인 범위와 미검증 항목은 [2026-11-15 통합 검증 기록](docs/landing-integration.md)을 참고하세요.

```powershell
npm.cmd run build
npm.cmd test
npm.cmd run preview
```

Vitest + Testing Library로 실제 HTTP 클라이언트를 사용하고 `fetch` 응답을 테스트 안에서 대체합니다. UUID, 6개 API의 경로·본문·헤더, 한국 시간, 입력 제한, AI 성공/실패/대기 취소, 저장 재시도, 저장 후 조회 실패, 작업 시작·완료·복원·수정, 지난 마감·부족 시간 표시를 검증합니다. 테스트 응답은 앱 실행 코드에 포함되지 않습니다. 이 테스트는 실제 Ollama 모델 출력이나 실서버 E2E 검증을 대체하지 않습니다.
