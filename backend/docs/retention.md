# 30일 보관 및 삭제 운영 절차

## 범위와 기본값

`sessions.started_at`, `video_judgments.created_at`, `events.created_at`, `tasks.created_at`을 기준으로 30일이 된 기록을 삭제한다. 세션이 삭제되면 생성 시각과 관계없이 연결된 영상 판단도 삭제한다. 영상 정정은 최초 생성일을 갱신하지 않는다. 설정은 자동 정리에서 유지하고, 사용자별 삭제 요청에 포함한다. 현재 실행 중인 세션도 30일 기준에 포함한다.

시각은 UTC로 비교한다. 기존 시간대 없는 ISO 시각은 기존 DB 계약과 동일하게 한국 시간으로 해석한다. 정확히 30일인 경계를 포함하고, 1마이크로초라도 덜 지난 행은 유지한다. 해석할 수 없는 시각은 무작정 삭제하지 않고 `invalid_dates` 건수로 보고한다. 기존 판단 생성일이 과거 코드의 정정으로 갱신됐다면 저장된 시각을 기준으로 처리하되, 부모 세션의 30일 삭제가 우선 적용된다.

기본 `RETENTION_MODE=preview`는 읽기 전용 집계다. 운영 DB 삭제를 승인하기 전에는 이 값을 유지한다. `RETENTION_MODE=apply`가 승인된 이후에는 FastAPI lifespan에서 시작 직후와 기본 60초 간격으로 정리한다. 재시작·중단 후에도 첫 실행에서 밀린 대상을 처리한다. 오류가 나면 다음 주기에 재시도하며, 로그에는 합계·기준 시각만 남긴다. `off`는 명시적 점검용 비활성 모드다.

승인된 활성화 이후에도 스케줄 간격·서버 중단·DB 잠금 때문에 삭제가 지연될 수 있으므로 작업 로그와 `invalid_dates`를 확인한다. 서비스 프로세스 관리자의 자동 재시작 설정과 실제 운영 볼륨 경로도 확인한다. 별도 cron 프로세스가 없어도 uvicorn 재기동 때 작업이 다시 구성된다. uvicorn worker가 여러 개면 중복 실행될 수 있으며 SQLite 쓰기 잠금·대상 재검증으로 일관성을 유지한다. 변경된 계획은 다음 주기에 다시 확인한다.

## 기존 기록 최초 정리

아래 명령은 **backend 디렉터리**에서 실행한다. 운영 서버의 실제 `DB_PATH`와 절대 경로를 사용한다. 로컬 예제 DB의 건수를 운영 DB 건수로 보고하지 않는다.

```bash
# 이 단계는 운영 DB를 생성·수정하지 않는다. 계획 파일은 새 파일만 허용한다.
python -m scripts.retention preview --db /data/mobonyong.db --plan /secure/retention-plan.json
```

출력의 `counts`, `invalid_dates`, `cutoff_utc`와 DB 경로를 운영자·사용자가 검토한다. 영상 판단 건수는 자기 생성일 만료와 부모 세션 연쇄 삭제를 합친 중복 없는 수다. 계획에는 원문 할 일·영상·이벤트 payload·사용자 ID를 넣지 않는다. 계획·요청 파일의 접근 권한은 담당 운영자로 제한한다.

**운영 DB 삭제에 대한 사용자 승인을 받은 다음** 적용한다. 최초 대량 정리 시에는 API 요청을 잠시 중단하고 진행 중 요청이 끝났는지 확인한다. 백업을 생성하려면 아래 선택 인자를 사용한다. 백업 경로가 이미 있으면 덮어쓰지 않고 실패한다.

```bash
python -m scripts.retention apply --db /data/mobonyong.db --plan /secure/retention-plan.json --backup /secure/new-before-retention.db
```

계획은 DB 파일·고정된 기준 시각·삭제할 행 집합의 fingerprint와 건수에 연결된다. 변경이 발견되면 전체 삭제를 중단하고 새 미리보기와 승인을 받는다. 삭제는 한 트랜잭션이며 실패하면 전체 롤백한다. 계획 시각을 최근으로 조작해 30일 미만 데이터를 삭제할 수 없도록 검증한다. 재실행할 때에는 새 계획을 만든다. 승인된 운영 설정에서 `RETENTION_MODE=apply`로 바꾸고 서비스를 재시작하면 향후 만료 데이터도 계속 정리된다.

삭제된 기록은 지표 계산에서도 제외된다. 기존 `/sessions`, `/judge`, `/judge/feedback`, `/events`, `/metrics`, 작업·계획 API 계약은 유지한다. 부모 삭제 후 늦게 도착한 AI 응답은 영상 판단을 다시 만들지 못하고 404로 처리한다.

## 사용자별 삭제 요청

1. `ymook38897@gmail.com`으로 비공개 요청을 받는다. 로그인 없는 서비스이므로 UUID 하나만 아는 것으로 본인 확인이 완료됐다고 판단하지 않는다. 요청 기기에서 식별 정보를 확인하는 절차와 신뢰할 수 있는 연락 경로를 통해 요청 권한을 확인한다. 공개 이슈·URL·일반 서버 로그에 사용자 ID를 남기지 않는다.
2. 사용자가 세션 종료와 감지·AI 중지를 직접 수행하도록 안내한다. 여러 기기라면 각 ID를 확인한다. 운영자는 새 요청 수신을 잠시 중단하고 기존 요청을 drain한 뒤 적용한다. 이는 진행 중 요청이 삭제 직후 옛 기록을 다시 남기는 일을 피하기 위한 절차다.
3. 확인된 ID 하나를 보호된 UTF-8 파일에 넣는다. ID 파일·계획은 승인된 담당자만 읽도록 보호한다. 생성일과 관계없이 해당 사용자의 모든 세션·판단·이벤트·할 일·설정을 미리 집계한다.

```bash
python -m scripts.retention preview --db /data/mobonyong.db --user-id-file /secure/request-user.txt --plan /secure/user-erasure-plan.json
# 대상·건수를 검토하고 해당 요청의 삭제 적용을 승인받은 뒤 실행한다.
python -m scripts.retention apply --db /data/mobonyong.db --user-id-file /secure/request-user.txt --plan /secure/user-erasure-plan.json
```

공개 HTTP 사용자 삭제 API는 추가하지 않는다. 기존 `X-User-Id`는 인증 수단이 아니며, 파괴적인 삭제 권한을 주지 않는다. 적용은 서버 접근 권한이 있는 운영자 CLI에서만 수행한다. ID가 다른 파일·다른 DB·새로 변한 대상에는 기존 계획을 사용할 수 없다. 적용 결과를 집계로 기록하고 사용자에게 완료를 알린다. 요청 및 백업 복원 재적용 기록은 승인된 비공개 운영 절차로 관리한다.

## 백업과 파일 잔존

이 작업은 기존 DB 파일·백업·볼륨·로그를 자동 삭제하거나 VACUUM하지 않는다. 적용 연결은 `PRAGMA secure_delete=ON`을 사용하지만 WAL·기존 저널·백업·호스팅 스냅샷의 별도 사본까지 자동 제거하지 않는다. 이 사본들의 보유 기간과 삭제는 운영 배포 전에 별도로 확인·승인해야 한다. 백업 복원 후에는 외부 요청을 받기 전에 30일 만료 데이터와 완료된 사용자별 삭제를 다시 적용한다. 승인된 사용자 삭제 후 불필요한 식별 자료의 보관도 최소화한다.

## 백엔드 담당자 인수 체크리스트

현재 로컬 검증은 pytest 45개와 프론트 빌드를 통과했다. 로컬 개발 DB 2개의 만료 대상은 0건이며 운영 건수는 미확인이다. 운영 접근·삭제·스키마 적용·배포는 보류 상태다.

- [ ] 운영 서비스·실제 `DB_PATH`·영속 볼륨·프로세스 재시작 방식과 worker 수를 확인한다.
- [ ] 승인된 별도 검증 환경에서 기존 DB 스키마 호환성을 확인한다. 새 `db.connect`가 세션 삭제 트리거를 생성하므로 운영 스키마 적용도 사전 검토·승인한다.
- [ ] 기본 `RETENTION_MODE=preview`에서 운영 DB의 읽기 전용 집계와 `invalid_dates`를 보고한다. 사용자 설정의 자동 삭제 제외와 세션 연쇄 삭제 건수를 확인한다.
- [ ] 백업·WAL·저널·호스팅 스냅샷의 보유 일정, 접근 권한과 복원 후 재정리 절차를 확정한다. 기존 백업은 임의로 제거하지 않는다.
- [ ] 최초 정리 대상과 건수에 대한 사용자 승인을 받은 뒤 적용 계획을 확정한다. 적용 전 진행 중 요청을 drain하고 변경된 계획은 다시 검토한다.
- [ ] 승인된 초기 정리 결과를 확인하고 지속 정리가 승인되면 서비스 설정에 `RETENTION_MODE=apply`를 저장한 뒤 재시작한다.
- [ ] 재시작 직후와 다음 60초 주기, DB 잠금 실패 후 재시도, 최근 기록 유지·기존 API·지표를 확인한다.
- [ ] 사용자별 삭제 요청의 비공개 본인 확인·ID 전달·계획 승인·결과 통지 담당자를 정한다. 문의 주소는 `ymook38897@gmail.com`이다.
- [ ] 개인정보처리방침의 운영 적용 전 검토 표시를 실제 적용 상태·시행일과 대조해 최종 확인하고, 별도 게시 승인을 받은 뒤 공개한다.

구현만으로 운영 DB의 과거 기록이 정리됐다고 보고하지 않는다. 기본 미리보기 모드의 배포는 데이터 삭제를 수행하지 않는다.
